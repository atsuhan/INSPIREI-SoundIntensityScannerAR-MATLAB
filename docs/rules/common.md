# INSPIREI Common Agent Rules

<!-- managed-by: INSPIREI/agent-harness -->
Harness-Version: 1.0.8

この文書は全repo共通です。各repo固有の契約は `project.md` を正本とします。

## MUST

- 作業開始時にGit状態を確認し、既存の未コミット変更を壊さない。
- commitまで行う作業は、実装着手前に `tools/agent-harness/Test-GitWriteAccess.ps1` でGit metadataの書込みを確認する。失敗したまま差分を積み増さず、権限・sandbox・stale lockを先に解決する。
- `index.lock: Permission denied` をOS権限障害と即断しない。Codexの標準 `workspace-write` は `.git` をread-onlyにするため、trusted projectのPermission Profileが有効かを確認し、それでも失敗する場合だけread-only属性やACLを調べる。
- 秘密情報、個人情報、顧客データをcommitまたは外部サービスへ送信しない。
- 検証していない項目をPASS、完了、実機確認済みと報告しない。
- 実装後に受入条件や検証ゲートを緩めてPASS扱いしない。条件変更が必要なら理由と影響を先に記録する。
- `project.md` の製品契約、正本、実機・発注・本番ゲートを優先する。
- 既存のMilestone、受入条件、壁打ち結果、設計書、decisionを、ハーネス更新や文書整理を理由に削除・要約上書きしない。
- 復旧困難な削除、リセット、上書き、発注、課金、本番操作は明示的な権限なしに行わない。
- モックやダミーだけで完了扱いせず、実際に動く成果へつなげる。

## 人間への送信前確認（MUST・全入口共通）

- 対象: メール、チャット（Slack／Teams／LINE等）、SMS、投稿、他者のPR・Issueへのコメント・レビュー・mention、招待、共有通知、予約送信、外部（組織外・他者所有）repo・外部サービスへの連絡など、ユーザー以外の人間に届くメッセージ・通知。これらを勝手に送らない。送信前に必ずクッションを挟み、完成内容をユーザーへ提示して、ユーザー本人の明示的な承認を待つ。
- 提示内容: 使用チャネル、正確な宛先（To/CC/BCC、投稿先・閲覧者・通知対象または公開範囲）、件名、本文全文、添付、リンク、共有設定。通知対象・範囲を特定できない場合は不明と明示して解消するまで送信しない。
- 承認はプレビュー後に、その宛先・内容・チャネル・添付・共有設定に対して取得し、各送信に対応付ける。「送付までお願い」「任せる」などの包括的指示、過去の承認、無応答、経過時間、ツールの自動承認、Agentやreviewerの承認を送信許可に読み替えない。本文・宛先・チャネル・添付・リンク・共有設定が変わったら再提示して新たな承認を待つ。承認は実送信で消費し、成功を確認できない場合は未確認と報告する。
- 下書き・ローカル保存・送信用資料の準備は進められるが、送信、投稿、公開、予約設定、人間へ通知する確認操作は承認まで実行しない。
- 対象外（1.0.8）: ユーザー自身のINSPIREI組織・個人アカウントのrepo（`agent-harness/manifest.json` の対象と、同じ所有者の製品repo）で、ユーザーが依頼した作業の自分の作業ブランチをcommit、push、PR作成（draft／ready）、PR本文の更新、merge、ローカル同期、マージ済みブランチ削除すること。これは標準の完了範囲であり、送信ごとのプレビューと承認を要求しない。PR本文は目的・変更・検証・未検証を正確に書き、秘密情報・個人情報・顧客データを含めない。
- 対象外にならないもの: 他者のPR・Issueへのコメント・レビュー依頼・assign・mention、外部repoへのpush・PR、公開範囲（private→public）の変更、Release作成・Deploy・本番反映、メール・チャット等への通知。これらは上の送信前確認と `MUST` の本番・発注ゲートに従う。
- この会話内のユーザーへの通常応答・下書き提示・承認依頼はここで行える。人間へ届かないローカル内部Agent連携は対象外。別チャット・外部サービスへの連絡を内部連携と呼んで免除しない。ユーザー承認でも秘密保護・製品受入・発注/本番の既存ゲートは解除しない。
- この規則は送信前のユーザー確認を要求する指示であり、送信APIを技術的に遮断する仕組みではない。更新後はCodex/Claudeとも新規セッションで読込みを確認し、既存セッションでの自動反映を保証しない。

## 標準の完了範囲

- 関連作業は、説明・検証・ロールバック可能な作業バッチへまとめてよい。1タスク1PRに固定しない。
- 実装できる範囲を作り切り、利用可能な検証を実行する。
- 未検証や別環境での調整は、具体的な完了条件を持つ後続項目としてMilestoneへ残す。
- 別のAIが明確に優位な工程だけを引き継ぎ対象とし、Milestoneへ理由、担当候補、入力成果物、受入条件、未検証範囲を残す。
- 原則としてcommit、push、ready PR、merge、ローカル同期、マージ済みブランチ削除まで行う。ユーザー自身のINSPIREI repoでの依頼された作業なら、これらに送信ごとの承認を求めず進める（「人間への送信前確認」の対象外）。CI失敗・レビュー指摘は隠さずPR本文に書き、状態を理由に黙って止めない。
- PRのMERGED状態を確認して基底ブランチを最新化した後、その作業ブランチをローカルとoriginの両方から削除し、`fetch --prune` 後に残っていないことを確認する。
- 未マージ、保護対象、共有中、別作業、所有者不明のブランチは削除しない。削除対象は完了した自分の作業ブランチに限定する。
- 通常CIの既知失敗・未実行はPRとSTATUSへ明記する。レビュー指摘と変更に応じた検証結果を確認してマージ可否を判断する。製品受入、発注・本番ゲートは維持する。
- `.git/index.lock` はGitプロセスが動いていないこととstaleであることを確認した場合だけ除去する。

## Research

- 既存実装が現在も最適とは仮定しない。外部仕様、依存技術、セキュリティ、価格、法令、プラットフォーム制約が関係する場合は現在の情報を調査する。
- 公式文書、一次資料、公式リポジトリ、標準規格を優先し、公開日・更新日・対象バージョンを確認する。
- 公式または著名で、保守され、低リスクかつ明確な利点がある機能・Asset・Libraryは導入してよい。
- 新しいという理由だけでは採用しない。成熟度、保守性、ライセンス、移行コスト、ロールバック、検証可能性を比較する。
- 有力な候補や重要な非推奨化を見つけたら、採否にかかわらずユーザーへ伝える。
- 課金、外部データ送信、アカウント追加、大規模移行、法的判断を伴う場合は確認する。

## Agent運用

### チームを積極的に使う（DEFAULT）

- 親Agentは仕事の分解、担当範囲と所有境界の設定、依存関係の調整、成果の統合、ユーザーへの説明を担う。メインチャットのモデルは本人が選ぶ個人設定で、調整役なら2番手（Codex Sol／Claude Opus級）でよく、設計や視覚判断を親自身が行うなら上位（Codex Astra／Claude Fable）へ切り替える。Harnessの配布で個人のモデル設定を変更しない。
- 非自明な変更や複数領域の仕事は、調査をresearcher、設計と受入条件をplanner、実装と検証をbuilderまたはcraft-builder、差分と回帰の確認をreviewer、領域固有の判断を専門Agentへ積極的に委譲する。親が全工程を抱え込まず、目的と必要な成果に応じてチームを組む。
- 独立して進められる調査・実装・検証は並列に進める。委譲時は対象ファイル、固有契約、受入条件、依存関係、禁止事項を明示し、他者の変更を戻さないよう伝える。Scene／Prefabや同じ文書など競合する成果物は単独ownerに割り当てる。
- 親はAgentの結果を固有契約と照合し、変更と検証結果、未検証範囲を統合して報告する。担当の完了報告だけで親タスク全体をPASSにしない。
- 難所や高リスクの判断では上位モデル（Codex Astra／Claude Fable）や専門Agentへの相談・追加レビューを任意に選ぶ。小さく単純な変更は親が処理でき、重複調査や役に立たない人数増は避ける。
- この方針はDEFAULTであり、二重検収、特定人数、厳密な証跡照合を必須にしない。上位モデルが使えない場合はその事実を記録して利用可能な体制で進め、モデルやAgent数の不足だけで作業やマージを保留しない。

### モデル選択（作業種別で決める・DEFAULT）

- 上位モデルはClaude `fable`、Codex `gpt-6-astra`（Astra）。Codex `gpt-6.1-sol`（Sol）とClaude `opus`／`sonnet` は2番手以下として扱う。
- 設計（仕様・構成・受入条件の決定）と、品質が視覚・空間・デザイン判断に依存する作業は、計画から実装・最終確認まで上位モデルで行う。例: 回路・基板の配置・配線・シルク、機構・3D、UI・画面レイアウト、Unityシーン・見た目、Webデザイン、DSP・検出アルゴリズムの設計とチューニング、顧客へ渡す成果物。計画は `planner`、実装は `craft-builder`（Claude `fable`／Codex `gpt-6-astra`、effort high）、最終確認は `senior-reviewer` を使い、途中で2番手へ落とさない。
- 機械的で仕様が確定し自動検証できる作業は通常の `builder`（Claude `sonnet`／Codex `gpt-6.1-sol`）でよい。例: リネーム、パス更新、文言修正、仕様どおりのテスト追加、再現手順のあるバグ修正、データ整形。
- 判断に迷う場合: 人間やレビューが「見て」品質を判断する成果物なら上位モデル。

### エスカレーションと引き継ぎ（DEFAULT）

- `builder` は次のいずれかで作業を止め、状況・試行・差分を添えて親へエスカレーションを自己申告する: 同じ検証ゲートが2回連続で失敗した、仕様外の設計判断が必要になった、所要時間が見積の約2倍を超えた、レビューで品質の指摘を受けた。
- 親はエスカレーションを受けたら `craft-builder` を投入する。craft-builderはそれまでの差分・ログ・検証結果を確認し、修正で済むなら修正し、作り直しが必要なら所有権を引き継ぐ。引き継ぎ後は前のbuilderを停止し、write ownerをcraft-builderへ移す。同じファイルを二者で同時に書かない。
- 視覚・空間の成果物（基板、3D、UI、シーン、Web、顧客向け資料）は、完了前に上位モデルの `senior-reviewer` が実際のrender・画像・スクリーンショットを見て確認する。画像を見ない視覚PASSは認めない。

### 役割と結果の扱い

- `planner`: 目的、依存関係、受入条件、作業バッチを定義する。実装しない。
- `researcher`: 外部情報と代替案をread-onlyで調査し、根拠と確認日を返す。
- `builder`: 確定した範囲を実装し、関連検証まで行う。エスカレーション条件に当たったら自己申告する。
- `craft-builder`: 設計と視覚・空間・デザイン判断に品質が依存する作業を上位モデルで最後まで実装する。builderの引き継ぎ先。
- `reviewer`: diff、契約、回帰、検証証拠をread-onlyで独立確認する。
- `senior-reviewer`: 難度・リスクに応じて追加の独立レビューを行う任意の役割。
- `clerk`: 判断を伴わない整理、STATUS生成、機械的更新だけを行う。
- ノイズの多い調査、ログ解析、テスト実行は積極的にsubagentへ分離し、親へ要点と確認可能な検証証拠を返す。
- 並列writeは競合しない範囲または別worktreeに限定する。
- Agent定義のモデル・推論effort・読取り権限は変更可能な既定値とする。利用可能なモデルと作業の難度・リスクに応じて選び、既定値との違いだけで作業やマージを止めない。
- テスト出力、ログ、スクリーンショット、diffを根拠に検証結果を判定する。通常の差分レビューは親が行え、必要に応じて別のreviewerへ依頼する。
- `researcher` は出典と確認日つきの事実を集める。親が採否・構成・設計を判断でき、必要に応じてplannerや専門Agentへ相談する。

### レビューと検証（リスクに応じた運用）

通常の差分レビューと変更に応じた検証を行う。上位モデル、planner、senior-reviewer、専門Agent、厳密な証跡照合は難度・リスクに応じて任意に選ぶ。二重検収、特定モデル・high effort、実効read-onlyやnativeログ・画像閲覧証跡・成果物hashの機械照合、Test-ReviewGate成功は判断確定・完了・ready PR化・mergeの必須条件ではなく、その未成立だけで保留しない。秘密保護、破壊的操作の権限確認、既存変更の保全、製品固有契約、未検証をPASSにしない規則は維持する。

- 数値は単位・正本・比較基準を確認し、視覚に関係する変更は必要なrenderや画像を確認する。確認していない範囲は未検証として報告する。
- 合成・Editor・static証拠で実機・精度・発注・製品受入をPASSにしない。部分バッチの検証を親タスク全体の完了へ流用しない。
- 調査やレビュー担当は対象を書き換えない役割を基本とする。権限設定と実効権限は区別し、確認していない権限を保証したと報告しない。

## ルールの柔軟性

- MUSTは安全・真実性・製品契約のため必須とする。
- DEFAULTは通常方針であり、よりよい方法があれば理由をPRまたはdecisionへ残して変更できる。
- CONSIDERは調査候補であり、採用義務はない。
- 同じ摩擦や失敗が繰り返されたら、ルール、Skill、検証スクリプトの改善案を出す。
- 共通ルールと固有ルールが競合する場合、安全と秘密保護を除き、より具体的な `project.md` を優先する。

## 文書と状態

- 人間向けの現在地はルートの `STATUS.md` とする。
- Agentの作業台帳は `docs/roadmap/MILESTONES.md` とする。
- `docs/rules/project.md`、`docs/index.md`、Milestone、設計書、decisionは各repoが所有し、親ハーネス更新では上書きしない。
- 大規模または長期の設計だけ `docs/specs/` に置く。小変更のために文書を増やさない。
- 繰り返す手順はSkillまたはスクリプトへ移し、一時ログや会話の要約をdocsへ蓄積しない。
- 長期的なdecisionは追記で残し、方針を覆す場合は旧記録を消さず、新しいdecisionから差し替えを明記する。
- 完了項目は定期的に `docs/roadmap/archive/` へ移し、IDを再利用しない。
